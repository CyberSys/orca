## 1. Verdict

**Ship with fixes.**

The branch's core thesis is correct and the fix is real: the merge-base path did map every registered repo through an unbounded `Promise.all` (`orca-runtime.ts@9eff3728:24744`) and only cached *successful* scans (`@9eff3728:24897`), so a deleted repo directory respawned `git` forever. Both are genuinely fixed, the code typechecks, and every touched suite passes.

But two of the prior review's claims are real functional regressions that I would not merge as-is, and one is a regression whose *deleted test* proves the invariant was previously protected on purpose. The prior review is broadly right on direction but overstates two claims and gets one backwards.

Nothing here is a crash or data-loss risk on the scale of C2 itself — the worst case is stale/purged **lineage** metadata and repos going silent for up to 5 minutes. Fixes 1 and 2 below are small and local.

### 1 — PARTIAL (real, but the prior framing is wrong on the hung-repo case)

`computeResolvedWorktrees` now creates one fleet-wide `AbortController` armed at `RESOLVED_WORKTREE_REPO_TIMEOUT_MS` (5s) for the whole sweep (`orca-runtime.ts:24794-24799`) and drains repos through `mapWithConcurrency(repos, 8, …)` (`:24802`). The old code gave each repo its own 5s `withTimeout` and started them all at once (`@9eff3728:24744,24764-24768`).

Where the prior review is **wrong**: for the *hung* case the outcome is identical. Old code: 40 repos all spawn, all hit 5s, snapshot is empty. New code: 8 spawn, 32 never start, snapshot is empty. Same result, 32 fewer `git` spawns — that is the fix working. The `40 hung repos → 8 spawns → []` test (`…scan.test.ts:360-393`) does not "lock in a regression"; it locks in the intended spawn bound.

Where the prior review is **right**: the regression is the *slow-but-healthy* fleet, which no test covers. Total sweep cost is now `ceil(N/8) × L` against a fixed 5s wall. At N=107 (the install size named in the commit message) the sweep truncates once per-repo latency exceeds ~370ms — plausible on Windows/WSL, where the code's own comments call `git worktree list` spawns expensive (`git/worktree.ts:685`, `#7225`). Repos past the cut return `buildWorktreeScanFailure(repo,'cancelled')`, which serves last-known cached worktrees when present (`:24824`, `:24981-24984`) — so on a warm cache this is invisible. On **cold start** those repos return `[]` and pop in over subsequent 1s sweeps.

Corroborating evidence this was a deliberate invariant that got dropped: the merge-base carried the comment *"mobile startup shares this path, so a slow repo scan degrades one repo's metadata instead of blocking all session loading"* (`@9eff3728:24763`). That comment is deleted, and the property it described no longer holds — one slow repo can now consume a slot and push later repos past the shared deadline.

Blast radius is bounded, and I checked this rather than assuming it: the only destructive consumer of a truncated snapshot, `pruneLineageForMissingRepoWorktrees`, is correctly gated on `scan.kind === 'success'` (`:24838`), and `refreshPtyWorktreeRecordsFromController` falls back to `session.worktreeId ?? persistedWorktree ?? inferredWorktreeId` before consulting the resolved list (`:25611-25618`), so a missing entry does not unbind a PTY. The damage is display/metadata only.

### 2 — CONFIRMED

`listRepoWorktreesForResolutionUncached` arms the per-repo `AbortController` at line `25130`, *then* awaits the slot at `25136`. Queue wait is charged to the git budget.

Within a single sweep this is inert (8 workers, 8 slots — nothing queues). It bites when `worktrees:listAll` (its own concurrency 8, `ipc/worktrees.ts:892`) overlaps the sweep on a **different** repo set: 16 requests contend for 8 slots and the 8 losers burn their 5s in the queue. Same-repo overlap correctly coalesces on `worktreeScanInFlight` and takes no second slot.

### 3 — CONFIRMED

An abort raised while waiting for a slot throws `createWorktreeScanAbortError()` (`:25211`, `:25227`), which is caught at `:25146` and classified: not `isNotGitRepositoryError`, and `isMissingRepoPathScanError` tests only for `ENOENT`/`ENOTDIR` (`:30795-30802`) — the message is `"Worktree scan timed out"`. So it falls through to `scan_failed` (`:25163`) and `recordWorktreeScanFailure` writes a backoff (`:25114`) escalating 30s → 60s → 120s → 240s → 300s (`:30791-30792`).

**A healthy repo that merely lost a slot race is recorded as a failing repo.** Combined with claim 2 this is the sharpest finding on the branch: local scheduler contention is laundered into durable per-repo silence. Mitigation that does exist: the backoff serves last-known cached worktrees (`:24981-24984`) and any worktree-change notification clears it (`:25309`), so the user sees stale rows, not empty ones.

Second half also confirmed: `settleWithAbort` (`:30897-30915`) only races a fallback — the underlying promise keeps running and can call `recordWorktreeScanFailure` long after the sweep returned `cancelled`.

### 4 — CONFIRMED, and more serious than the prior review stated

Joiners get the raw mapped promise (`:25063`) and never see the `isCurrent` re-check that protects the originator (`:25093-25102`). So after an invalidation lands mid-scan, the originator correctly returns `{kind:'failure', reason:'invalidated'}` while a joiner returns `{kind:'success', origin:'scan', worktrees: <pre-change list>}`.

That value reaches two side-effect sites:

- `ipc/worktrees.ts:924` — `shouldUpdateKnownWorktreeState = scan.kind === 'success' && scan.origin === 'scan'` → runs `rememberLocalWorktreeRoots` **and** `pruneLineageForMissingRepoWorktrees` on the stale list. A worktree created during the scan is absent from that list, so its lineage is purged and its parent's `instanceId` is re-randomized (`orca-runtime.ts:24912-24927` is the equivalent runtime path).
- `orca-runtime.ts:24838` — the sweep itself can be the joiner, with the same effect.

This is a **regression, not a pre-existing gap**. The merge-base IPC path tracked exactly this: `listDetectedGitWorktrees` carried an `invalidated` token and returned `fresh: !scan.invalidated`, and gave joiners `fresh: false` unconditionally (removed hunk in `ipc/worktrees.ts`). The proof is in the deleted tests — `git diff 9eff3728a3 -- src/main/ipc/worktrees.test.ts` removes:

```
- it('does not run fresh-scan side effects from a detected scan invalidated while in flight', …)
- it('does not retain invalidated detected scans after they settle', …)
```

The replacement (`…scan.test.ts:506-543`, *"marks an invalidated scan as a failure"*) covers the **originator** only. The joiner invariant lost both its implementation and its test in the same change.

### 8 — REFUTED (prior review's dismissal was correct)

I re-derived every path in `withLocalWorktreeScanSlot` (`:25194-25248`):

- `acquire` throws synchronously on a pre-aborted signal (`:25210-25212`) → thrown before `try` → no increment, no release. Balanced.
- `acquire` returns `undefined` after incrementing (`:25213-25216`) → `try/finally` releases. Balanced.
- `acquire` returns a promise that **rejects** on abort (`:25222-25228`) → `await waiting` throws *before* the `try` block → no release, and the waiter was spliced out and never incremented. Balanced.

The `if (waiter.signal.aborted)` branch in `releaseLocalWorktreeScanSlot` (`:25240-25243`) is unreachable defensive code — abort listeners fire synchronously, so an aborted waiter has already spliced itself out — but unreachable is not incorrect. There is no double-release and no underflow. **No fix needed.**

## 3. Additional findings the prior review missed

**A. The idle TTL has no upper cap, contradicting the documented 5-minute ceiling.** `resolveWorktreeScanCacheTtlMs` floors with `Math.max` but never caps (`:30772-30775`). Solving `(N−a)/(60−2a) × 60000 ≥ 300000` gives: at N=107 local repos, idle TTL exceeds 5 minutes once **a ≥ 22 actives**, and reaches **~39 minutes at a = 29** (78/2 × 60s). It is also non-monotonic — 29 actives → 39min for idle repos; 30 actives → 107s for everyone. The commit message says *"capped at 5min"*; nothing implements that. Consequence: an out-of-band `git worktree add` in an idle repo can stay invisible for tens of minutes. (Orca-initiated changes are unaffected — they invalidate.)

**B. Eager fallback construction on the success path.** `buildWorktreeScanFailure(repo,'cancelled')` is computed at `:24824` for **every** non-folder repo on **every** sweep, before the scan is even attempted and regardless of outcome. For an SSH repo with no cache entry it walks `store.getAllWorktreeMeta()` in full (`:25268-25293`). At 1s snapshot TTL that is O(repos × all-worktree-meta) per second, on the exact path this branch exists to make cheaper. Move it behind the failure branch.

**C. That same call omits `generation`/`runtimeKey`.** Every other `buildWorktreeScanFailure` caller passes both (`:25071`, `:25074`, `:25082`); `:24824` passes neither, so `matchingCached` accepts any cached entry (`:24972-24977`). The generation axis is safe in practice (invalidation deletes the cache entry), but a `runtimeKey` change — e.g. a WSL distro switch — leaves the entry in place, so a cancelled scan can serve worktrees scanned under the previous runtime. Narrow; inconsistent with its siblings.

**D. Loss of the git-layer shared-scan fence for non-runtime callers (#7225).** The merge-base runtime called `listRepoWorktrees(repo, opts)` with **no** signal, so it joined the `inFlightWorktreeScans` dedupe in `listWorktrees` (`git/worktree.ts:736-758`). The new path always passes a signal and calls `listWorktreesStrict` directly (`:25140`), which bypasses that map entirely. Runtime↔IPC dedupe is preserved (better, in fact) by `worktreeScanInFlight`, but `listRepoWorktrees` callers — `memory/hydrate-local-pty-registry.ts:80`, `ipc/filesystem.ts:339`, `ipc/filesystem-auth.ts:190`, `ipc/hosted-review.ts:46,60`, `workspace-space-analysis.ts:789`, `ipc/workspace-cleanup-scan.ts:246` — can no longer collapse into the runtime's scan. On Windows cold start (`hydrate-local-pty-registry` runs per repo) that is a real, if modest, extra spawn per repo. Worth a sentence in the PR body either way, since `:25312` still advertises *"the Windows spawn fence (#7225)."* Note `listWorktreesStrict`'s body is otherwise byte-identical to `readTranslatedWorktreeGraph` (`git/worktree.ts:650-658` vs `:792-796`), so there is no result-shape drift — the only delta is error handling, which is the intent.

**E. IPC-side coverage is now stubbed out.** `worktrees-windows.test.ts` mocks `listRepoWorktreesForDetection` wholesale (+6 lines), and `worktrees.test.ts` drops 11 tests. Combined with finding 4's deleted joiner test, the IPC↔runtime seam is now exercised only from the runtime side.

**F. Non-finding, checked and cleared.** `authoritative: scanSucceeded` / `source: 'metadata-fallback'` (`ipc/worktrees.ts:1071-1074`) is a valid union member (`shared/types.ts:653`), and its only behavioral consumer, `pruneLastVisitedTimestamps` (`App.tsx:1074-1076`), *keeps* timestamps when non-authoritative. That change is strictly safer than the old unconditional `authoritative: true`.

**G. Non-finding, checked and cleared.** The 5s detection max-age (`DETECTED_WORKTREE_SCAN_MAX_CACHE_AGE_MS`) does floor the runtime TTL and so partially bypasses the 60/min budget — but `fetchAllWorktrees` is event-driven (mount / repo-count change / settings), not interval-polled (`App.tsx:1072`, `sidebar/index.tsx:86,113`, `AutomationsPage.tsx:1065`). It is a ceiling, not a cadence. Matches the merge-base's own 5s IPC cache, so no regression.

### How the fleet deadline works now (fix 4, revised)

A flat one-wave deadline was wrong once the concurrency cap turned the sweep into waves: a healthy
107-repo fleet lost every repo past ~370ms of scan latency on a cold cache. The per-repo deadline
(armed at slot acquire, fix 2) bounds each scan; the fleet deadline now bounds the *sweep* at
`RESOLVED_WORKTREE_FLEET_MAX_WAVES` (3) per-repo budgets — enough for 107 repos at ~1s each, while
still capping how long a wedged fleet can hold the resolved snapshot open.

Fleet abort now also cancels the per-repo controllers, so slots free the instant the sweep gives up
instead of staying pinned for the remainder of each per-repo budget. Aborted scans stay `cancelled`
(never backed off), so the next sweep simply rescans them.

Truncation is a stated contract, and the tests pin both sides:

- 107 repos × 700ms → all 107 resolve on a cold sweep (14 waves inside the 15s budget).
- 40 repos × 200ms → all 40 resolve, 40 spawns.
- 40 repos × 4s → snapshot truncates to 24, **32** spawns (the 8 past the deadline are skipped, not
  spawned-then-abandoned), no backoff written; the next sweep rescans the 16 uncached and returns 40.
- 40 hung repos → 2 waves of 8 = 16 spawns, stopping at 10s (round 3: two consecutive barren waves),
  peak concurrency 8, every slot free at the deadline, no backoff.
- 40 repos whose first 8 are wedged and whose remaining 32 are healthy at 200ms → all 40 spawned,
  32 resolve, and five consecutive sweeps keep returning 32 (round 3).
- Repos with a live pane are scanned first, so truncation lands on idle repos.

### 1 — a caller's deadline may only abandon its own wait

`worktreeScanInFlight` hands joiners the originator's promise, so binding the per-repo
`AbortController` to the originator's `fleetSignal` let a background sweep's deadline cancel an
IPC/detection caller that had no deadline at all. The scan is now refcounted: the in-flight entry
owns the controller and a `waiters` count (`orca-runtime.ts`, `joinWorktreeScan`). Every caller
registers as a waiter; a caller with a `fleetSignal` deregisters when that signal fires and only the
*last* departing waiter aborts the underlying git/relay call. A caller with no signal never walks
away, so it alone keeps the scan alive. The sweep still frees its slot the instant its deadline
fires (it is normally the only waiter), so the round-0 zombie-slot fix is preserved. A scan whose
controller has already aborted is no longer joinable — a late caller starts a fresh scan instead of
inheriting a corpse. Pinned by *keeps a joined scan alive when the originating sweep hits its fleet
deadline* (the promoted round-1 repro).

### 2 — waves are earned, not granted *(superseded by round 3, § "barren waves")*

The sweep no longer arms one flat 3-wave deadline. It arms one per-repo budget at a time and stops
early once the fleet looks wedged (`RESOLVED_WORKTREE_FLEET_MAX_WAVES` is still the ceiling). Cache
hits deliberately do not count as productive: they cost no wave, so counting them would buy time for
a fleet whose live repos are all wedged. `resolveResolvedWorktreeFleetTimeoutMs` is replaced by
`resolveResolvedWorktreeFleetWaveCount`. **Round 2 stopped after a single barren wave, which was too
aggressive — see round 3.**

### 3 — SSH scans are bounded

`provider.listWorktrees` was awaited raw: no deadline, no abort, while still being charged a wave
budget and holding one of the 8 sweep workers. It now runs under the same
`RESOLVED_WORKTREE_REPO_TIMEOUT_MS` and the same per-repo controller (so the refcount abort in fix 1
reaches it too), and a timed-out relay settles as `cancelled` — contention, never a backoff — with
the stored SSH worktrees as fallback.

### 4 — sweep priority vs rate budget are now separate sets

`WorktreeScanFleet` carries `activeRepoIds` (every repo with a live pane, tab, or active session,
SSH included) for the scan-order sort, and keeps `activeLocalRepoIds` for the local spawn-rate
budget. An SSH workspace with a live pane no longer sorts behind every idle local repo.

The commit message on `5a8f3e6f4b` was not amended (this dispatch forbade committing). It still
claims `listReposMissingOnDisk` (0 hits in `src/`) and *"Explicit user-triggered scans never read or

## 7. Round 3 — fixes for the independent review (`.orca/review-round-2.md`)

### 1 — barren waves: a wedged head no longer starves the tail *(blocking; superseded by round 4 § 1 — the barren-wave rule is gone)*

Round 2's rule ("buy the next wave only if the elapsed one completed a scan") could not tell a wedged
*fleet* from a wedged *head of the scan order*. With ≥8 wedged repos sorting first, wave 1 completed
nothing, the fleet aborted at 5s, and **every repo behind them was returned `cancelled` without ever
being spawned** — no cache written, no backoff written (`cancelled` is exempt by design), identical
sort position next sweep. Self-perpetuating: 40 repos with 8 wedged and 32 healthy at 200ms gave 8
spawns and 0 worktrees, on five consecutive sweeps. Round-2 fix 4 made it easier to hit, since active
SSH repos now sort first and fix 3 gives them a 5s deadline a hung relay reliably burns.

The sweep now aborts only after `RESOLVED_WORKTREE_FLEET_BARREN_WAVE_LIMIT` (**2**) *consecutive*
barren waves, or when `RESOLVED_WORKTREE_FLEET_MAX_WAVES` runs out. The wedged wave's own per-repo
deadlines free its slots at 5s, so wave 2 gets spawned either way and a healthy tail lands at ~5.8s;
a genuinely wedged fleet stops at 10s instead of round-1's 15s. A productive wave resets the count.

Pinned by two new tests — *scans the healthy tail when the first wave is wedged* (40 spawns, 32
resolved) and *keeps surfacing the healthy tail on later sweeps while the head stays wedged*
(`[32,32,32,32,32]`) — both promoted from the reviewer's repro. The existing wedged-fleet test now
asserts two waves / 16 spawns / a 10s stop, and *frees every slot as soon as the fleet deadline fires*
moves to the 15s ceiling (its wave 1 is productive, so only one barren wave elapses before the cap).

### 2 — `RESOLVED_WORKTREE_FLEET_MAX_WAVES` is a coverage ceiling, not a wedge guard *(round 4 makes it the only bound)*

Left at 3, comment corrected. The barren-wave limit is what bounds a wedged fleet; the cap only bounds
a *productive* one, at ~120 repos per sweep at 1s latency (400 at 300ms). Beyond that the tail
truncates and lands on the next sweep — the same stated contract as the 4s-latency case, and the trade
we want over holding first paint open longer.

### 3 — dropping an in-flight entry now aborts its controller *(the "costs them nothing" claim is wrong; corrected in round 4 § 2)*

`invalidateWorktreeScanCacheForRepo`, `invalidateSshWorktreeScanCacheInternal`, and
`pruneWorktreeScanState` deleted live `worktreeScanInFlight` entries without aborting them. Once out of
the map the controller is unreachable, so the git process ran its full 5s budget holding one of the 8
slots while its replacement queued behind it — worst under the invalidation churn of a worktree-change
burst. All three now go through `dropWorktreeScanInFlight`. Waiters already receive `invalidated` on
these paths, so cancelling costs them nothing; the type doc comment was corrected to match.

### 5 — `WORKTREE_SCAN_CONCURRENCY` comment

Dropped the false "including RPC scans": SSH/RPC scans take no slot. They are bounded by the sweep's
worker pool and their own per-repo deadline.

bullet now matches the code again. Issue 6 needs one sentence in the PR body: **SSH provider errors are
now negatively cached (30s→5min) where merge-base retried at the normal 30s TTL; a reconnect — SSH

## 8. Round 4 — fixes for the independent review (`.orca/review-round-3.md`)

### 1 — the fleet deadline is a wall clock again, never a wedge detector *(blocking)*

Round 3 bounded the starvation instead of removing it: `BARREN_WAVE_LIMIT = 2` tolerates a wedged head
exactly one wave wide. A **16-wide** wedged head still made waves 1 and 2 both barren, so the fleet
aborted at 10s and the healthy tail was never spawned — `[0,0,0]` across three sweeps, 24 healthy repos
starved forever, for the same self-perpetuating reason as round 3 (`cancelled` writes no backoff, so
the wedged prefix sorts identically next sweep).

The generalisation is that *every* mid-sweep wedge signal is ambiguous: "this wave completed nothing"
reads the same for a wedged fleet and for a wedged prefix — a hung relay, a down WSL distro, a dead
network mount holding a clustered block of repos — and giving up on the second starves the healthy
tail permanently. So `RESOLVED_WORKTREE_FLEET_BARREN_WAVE_LIMIT` and the `armFleetWave` recursion are
**deleted**. One `setTimeout` at `resolveResolvedWorktreeFleetWaveCount(localRepos) × 5s` arms the
fleet controller and nothing else ends the sweep early. Wedged repos are bounded by their own per-repo
deadline, which frees their slot and lets the tail spawn behind them.

Measured against the reviewer's own probes (fake timers, 200ms healthy latency, 40 repos):

| Case | Round 3 | Round 4 |
|---|---|---|
| 8 wedged + 32 healthy | 32 resolved, 40 spawns | 32 resolved, 40 spawns |
| 9 wedged + 31 healthy | `[31,31,31]` | `[31,31,31]` |
| **16 wedged + 24 healthy** | **`[0,0,0]`, 48 spawns** | **`[24,24,24]`, 72 spawns** |
| 40 wedged (fully wedged) | stops at 10s, 16 spawns | stops at 15s, 24 spawns |

Pinned by a new product test — *scans the healthy tail behind a wedged head wider than the concurrency
cap* (`[24,24,24]` over three sweeps) — plus the rewritten *aborts timed-out git processes before
freeing slots and stops a wedged fleet at the ceiling* (8 → 16 → 24 spawns, stop at 15s).

**The cost, stated plainly.** A fully wedged fleet now spends the whole 15s ceiling instead of 10s and
spawns 24 git processes instead of 16 — worse than round 3 on that one case, and the reason round 3
existed. It is still inside the "≤15s, prefer ~10s" bar on the hard requirement only. Small fleets are
unaffected: ≤8 local repos still stop after one 5s deadline, ≤16 after two.

**Residual cliff (not fixed, measured).** Three waves of slots is 24 concurrent scans, so a wedged
prefix of **≥24 repos** still consumes every wave and starves the tail on every sweep, forever:

```
24 wedged + 16 healthy → [0,0,0] over three sweeps, 24 spawns per sweep
20 wedged + 20 healthy → [20,20,20]                (below the cliff, tail lands)
```

The cliff moved 8 → 24; it did not disappear, and it cannot be closed by any wave-counting rule for the
reason above. Closing it needs one of: (a) rotating the sweep's start offset per sweep so a wedged
prefix cannot occupy the head every time, (b) a *cross-sweep* wedge record — a repo cancelled by the
fleet deadline N sweeps running gets deprioritised, which is a backoff in everything but name and must
not feed `worktreeScanBackoff`, or (c) exempting repos with no cached worktrees from the ordering
penalty so a cold repo is never permanently behind a wedged one. All three are behaviour changes
outside this branch's scope; (b) is the one I would build.

### 2 — invalidation no longer kills a scan its caller is still waiting on *(blocking)*

Round 3 § 3 claimed "waiters already receive `invalidated` on these paths, so cancelling costs them
nothing". That is false against a signal-honouring git: the abort makes the scan return **no**
worktrees, and `invalidateWorktreeScanCacheForRepo` has already deleted the cache entry the
`invalidated` fallback is built from — so the waiter gets `fallbackWorktrees: []` where the completing
scan would have handed it the real list. An empty-then-repopulate blink, on exactly the `.git` mutation
that triggered the invalidation.

The reviewer's own suggested fix (drop the in-flight entry *before* deleting the cache) does not work
and I verified why rather than assuming: `controller.abort()` runs its listeners synchronously, but the
fallback is computed in a `.then` microtask, so the synchronous `worktreeScanCache.delete()` later in
the same function still lands first. Used the third option instead — `dropWorktreeScanInFlight` now
follows `joinWorktreeScan`'s existing rule and aborts only when `entry.waiters <= 0`:

```ts
const entry = this.worktreeScanInFlight.get(repoId)
this.worktreeScanInFlight.delete(repoId)
if (entry && entry.waiters <= 0) {
  entry.controller.abort()
}
```

A waited scan now completes and its caller gets `{reason: 'invalidated', fallbackWorktrees: <real
list>}` — better than the cached list the reorder would have produced, since it is the *fresh* one. The
slot is still bounded: a waited scan frees it at its own per-repo deadline, and the round-3 motivation
(don't orphan a git process holding a slot with nobody left to want it) survives unchanged for the
unwaited case. Verified end to end on the reviewer's probe: `abortedAtInvalidation = false`, fallback =
the real worktree.

Both round-3 tests that mocked scans **without** honouring `options.signal` now use a signal-honouring
mock (`signalHonouringStrictScans` in the shared harness), so neither can pass by ignoring a
cancellation production actually sends. Under the old product code they fail with
`fallbackWorktrees: []`.

Note on the reviewer's probe B: it still records `fallbackWorktrees: []`, but that is now the **per-repo
deadline** firing at 5s, not invalidation — that probe never resolves its scan, so nobody ever supplies
a list. Probe B3 (same setup, scan resolved after the invalidation) is the discriminating one.
